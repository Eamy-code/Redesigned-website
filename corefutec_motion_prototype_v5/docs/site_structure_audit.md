# コアフューテック株式会社 Webサイト構成調査・改善提案

調査日：2026年10月23日（日本時間）  
対象：`https://www.corefutec.co.jp/` と `https://www.recruit.corefutec.co.jp/` を一つの企業サイトへ統合  
目的：静的サイトによる全面リニューアルに先立ち、コンテンツ構成と情報設計を確定するための初期調査

> 本書は本体の公開サイトマップ、採用サイトの公開ナビゲーションと検索で確認できたページに基づく一次調査です。WordPress管理画面、サーバー、アクセス解析、Search Console、フォームの送信先、非公開・非掲載ページは確認していません。本体26件＋採用サイトのナビ掲載8件＋検索で見つかった旧版らしき1件という**計35件のURL候補**を把握したもので、両サイトの全URL数と断定しません。削除・統合・文言変更は提案であり、現行サイトには変更を加えていません。

## 1. 結論

現行サイトの強みは、1983年創業のソフトウェア検証実績、ISTQBプラチナ・パートナー認定、自社のテスト技術基準、ソフトウェア開発・ログ解析・セキュリティ診断・自社製品まで持つ事業の広さです。

一方、Webサイトの構成上は、初めて訪れた企業担当者が「何を依頼できるか」「自社のどんな問題を解決できるか」「相談するとどう進むか」を短時間で理解するための情報が不足しています。技術説明は充実していますが、ページが長く、相談に進むための導線や要約が弱めです。

**推奨方針：企業サイトと採用サイトを一つの情報設計・デザインシステムへ統合する。** 主要サービス3領域を再整理し、強み・導入の流れ・FAQを補強するとともに、採用専用の入口を設けます。採用情報は単純に会社案内へ混ぜず、求職者向けのストーリーと導線を保持します。公開時は両ドメインの既存URLを保護し、統合先へ301リダイレクトする移行計画を作成します。

## 3. 構成上の課題と改善優先度

| 優先度 | 観察・根拠 | 推奨改善 |
|---|---|---|
| 最優先 | トップは「第三者検証」の説明が中心で、その他事業の理解にはスクロールが必要 | 3つの主要事業と自社製品を冒頭近くで明示し、対象顧客の課題から探せる入口を作る |
| 最優先 | サービス説明は技術の種類・特徴が豊富だが、依頼の進め方や成果物の説明が少ない | 「ご相談から納品まで」「何を提供するか」を新設 |
| 最優先 | 実績・信頼の材料は散在（1983年創業、認定、取引先、メディア） | 強み・実績のハブを作り、確認可能な情報をひと目で伝える |
| 高 | ログ解析とセキュリティ診断が同じ長いページ内に収録 | まず目次とアンカーで明確に分ける。必要なら2つの詳細ページに分割 |
| 高 | 現行の会社案内ページは下層ページへの入口が主 | 事業姿勢・理念・人・歩みをつなぐコンテンツに変える |
| 高 | 問い合わせはフォーム中心で、相談前の不安を解消するFAQが不足 | よくある質問、相談内容例、対応の流れを追加 |
| 高 | トップにお知らせとコラムが混在し、最新掲載例が2023〜2024年 | お知らせとナレッジを分け、更新計画と表示ルールを定める |
| 中 | トップからのリンクに `/wp/` を含む経路が見られる | 正規URLと転送挙動を調査。内部リンクを統一 |
| 中 | 技術サービスの説明文が長文中心 | 章見出し、図、カード、目次、ページ内ナビゲーションで整理 |
| 中 | 商品ページから外部の商品専用サイトへ遷移する | 外部リンクであることを明確にし、ブランドのつながりを保つ |
| 最優先 | 採用情報が別ドメインに分かれ、企業サイトとのデザインやナビゲーションが異なる | 本体の `/recruit/` に統合しつつ採用専用の情報導線を確保 |
| 高 | 採用ページは社員インタビュー・仕事内容・研修制度が充実する一方、社員情報・取材時点が2022〜2024年中心 | 調査年を残し、写真・在籍状況・募集条件を確認してから更新 |

上記は公開コンテンツを読んだ情報設計上の評価です。SEO順位・問い合わせ率・離脱率の実測評価ではありません。

## 5. 統合・縮小・削除を検討する箇所

1. **トップとサービスページの同趣旨の説明**：削除ではなく、トップでは短い要約、詳細は専門ページに集約。
2. **会社案内の単純なリンク一覧**：残すURLの内容を刷新。独立した5下層ページは当面維持。
3. **技術用語を網羅した長文**：一律削除せず、重要度に応じて要約＋詳細・開閉パネル・目次に整理。検索流入に配慮。
4. **終了済みイベントのお知らせ**：トップに大きく表示しない。履歴として記事と一覧は維持し、年度で整理。
5. **古い表現、重複した肩書・年数・認定情報**：各所に散らばる値の更新源を統一。掲載事実を検証した後に修正。
6. **古いリンク・不明な埋め込み・不要なソーシャル導線**：動作確認後に削除候補を決定。
7. **採用の重複募集要項**：`recruit.html` と `recruitn.html` は募集条件の差を確認し、正式な募集情報へ一本化する候補。旧URLには転送を設定。
8. **採用インタビューの旧情報**：削除よりも取材年月の明示、退職者の掲載確認、最新取材の追加を優先。

**現時点で恒久削除を推奨する公開URLはありません。** 検索流入・被リンク・管理上の必要性の確認なしに消す判断はしません。

ヘッダーの第一階層はできるだけ短くします。たとえば「サービス」「強み・実績」「自社製品」「企業情報」「採用情報」「お知らせ」「お問い合わせ」を主導線とします。企業担当者向けと求職者向けでは期待する情報が異なるため、採用は独立したトップと分かりやすい入口を持たせます。モバイルでは階層を浅くします。

## 7. 静的サイト制作と後日のWordPress化に向けた設計

- 両ドメインの確認候補35URLを、**企業トップ／事業／強み・事例／会社情報／記事一覧・本文／採用トップ／仕事内容・インタビュー／募集要項／フォーム／法務・資料**などの共通テンプレートに分類して制作。
- ヘッダー・フッター・パンくず・カード・CTA・目次・見出し・フォームを共通部品化。
- 更新されるお知らせとコラムは、最初から日付・分類・タイトル・本文・画像などのデータ項目を意識して設計。
- WordPress移行時には、静的デザインをテーマ化し、投稿・カテゴリ・固定ページをCMS管理にする。アニメーション自体は静的段階のCSS/JavaScriptで実装可能。
- 現行URLの維持を第一候補とし、変更が必要なときは `旧URL → 新URL` の対応表と301転送を用意。
- 採用ドメインの旧URLには原則として新しい本体ドメインの個別ページを一対一で対応させる。単純にすべてを採用トップへ転送しない。
- 問い合わせフォームは静的デザイン段階では見た目のみで、実送信は行わない。WordPress化時に送信・通知・迷惑送信対策・同意取得を検証。

## 8. 次に必要な確認事項

1. WordPress管理画面のページ／投稿一覧を確認し、非掲載URL・下書き・リダイレクト・添付資料を追加で棚卸し。
2. Google Analytics／Search Console等で流入上位・問い合わせにつながるページを確認。
3. 実績事例の掲載可否、写真・ロゴ使用権、認定資格・肩書・会社データの最新性を確認。
4. お知らせ更新頻度、WordPress管理項目、一般問い合わせ・採用応募フォームの送信仕様を確認。
5. 以上を反映してサイトマップ第2案と、全URLの移行マトリクスを確定。
6. 採用サイトの全ファイル一覧（特に旧版 `recruitn.html`）を確認し、職種、人数、給与、待遇、選考フロー、取材済み社員の公開許可を人事担当者と照合。
7. 旧採用ドメインの管理権限、DNS、HTTPS、転送設定、求人媒体に掲載したリンクの洗い出しを行う。
