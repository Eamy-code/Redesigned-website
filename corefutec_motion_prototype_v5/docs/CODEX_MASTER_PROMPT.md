# Codex 実装指示書：コアフューテック企業・採用サイト統合／現行情報反映

あなたは、BtoBテクノロジー企業のコーポレートサイト制作に精通したWebディレクター、コンテンツエディター、フロントエンドエンジニアです。

**依頼内容：このZIPに入っている静的サイトを基に、現行企業サイトと採用サイトの情報を調査・検証・必要に応じて文章改善し、新サイトに正確に反映してください。調査だけで終わらず、情報が確認できた範囲を実際に実装してください。**

ただし**サイトのデザインコンセプトを勝手に作り直さないこと**。まず既存デザインと設計Markdownを理解してください。WordPress化や公開は今回行いません。

## 0. 作業前に読む資料・優先順位

1. `README.md`：現在の静的プロジェクトの構成、実行方法、未実装事項。
2. `docs/DESIGN_VARIATION_MAP.md`：**現行v4の最優先ビジュアル指針**。ページごとにデザインが異なることが必須です。
3. `docs/new_sitemap_proposal.md`：企業・採用統合のページ構成、追加・統合候補、旧URL→新URLの移行案。
4. `docs/site_structure_audit.md`：以前の公開URL調査。**35件は候補であり完全な全URL一覧ではありません**。再調査が必要です。
5. `docs/design_system_v1_legacy.md`：初期検討資料。**古い提案**のため、現行v4と矛盾した場合はv4の実装・`docs/DESIGN_VARIATION_MAP.md`を優先してください（例：フォント、巨大見出し、カード表現など）。
6. `build.mjs`、`assets/css/style.css`、`assets/css/page-variants.css`、`assets/js/motion.js`：現在の生成構造、見た目、実際の動作を把握するために読むこと。

資料間に矛盾があれば勝手に混ぜず、`docs/DECISIONS_AND_OPEN_QUESTIONS.md`へ記録してください。上記資料の内容も無条件に事実とみなさず、現行公式サイトとの照合を行ってください。

## 1. 調査する現行サイト

- 企業サイト：`https://www.corefutec.co.jp/`
- 採用サイト：`https://www.recruit.corefutec.co.jp/`
- 各サイトのサイトマップ、グローバルナビ、フッター、ページ内リンク、記事一覧・ページネーション、PDF、公開画像等の**対象範囲**を確認。
- 現行サイト内で見つかる関連ページは、以前の35 URL候補に含まれていなくても調査対象に追加。

調査結果を `docs/CONTENT_INVENTORY.md` またはCSVにまとめ、**旧URL、ページ名、H1/H2、原文、メタ情報、画像・ファイル、リンク、取得日時、出典URL、新URL、移行可否、要確認事項**を追跡できるようにしてください。収集不能・閲覧不可のページは「未取得」と明記し、推測で補完しないこと。robots.txtやサイトの制約を尊重してください。

## 2. 文章の編集方針（重要）

読みやすさ・説得力・構成の改善は**積極的に許可**します。自然な日本語への言い換え、冗長さの削減、見出し、要約、CTA、見せる順番の改善を行って構いません。

一方で、以下は禁止します。

- **事実の追加・変更、技術的な意味・業務範囲の変更、資格・数値・顧客名・実績・社歴・採用条件の創作**。
- 「ソフトウェアテスト・第三者検証」を、根拠なく**自動車の走行テスト・車両試験・製造ライン検査**等と混同すること。
- ソフトウェア開発と品質保証、第三者検証、ソリューションを根拠なく同じサービスとして説明すること。
- 「品質を確認する」を「品質を保証する」など、責任・成果・保証範囲を強めてしまう言い換え。
- 実際には確認していない成果事例、取引先ロゴ、社員コメント、具体的なテスト手法・開発言語を追加すること。

編集の判断基準：

- A. **同義の読みやすさ改善**：実装して構いません。原文と改善案を記録。
- B. **意味が変わる可能性がある専門的・法的・採用上の変更**：提案はして構いませんが、承認前に確定表現として実装しないこと。
- C. **出典がない記述**：作成しないこと。「要確認」として報告。

`docs/CONTENT_CHANGE_LOG.md` に、変更したページ、**現行原文・改善文・変更理由・出典URL・判定(A/B/C)** を記録してください。全ての助詞まで記録する必要はありませんが、意味・訴求・条件に影響する変更を追跡できることが必須です。

## 3. 情報設計・移行方針

- 新サイトの基本ドメインは `www.corefutec.co.jp`、採用情報を `/recruit/` 配下に統合。
- 企業サイトの既存URLは原則維持。採用旧ドメインからは旧URL単位で新URLへの301方針を整理（**この工程では実際の転送設定はしない**）。
- `/services/`、`/strengths/`、`/process/`、採用各ページ等は設計資料に従う。ただし、調査で発見したページや不足項目は追加提案する。
- 既存の個別記事・技術コラム・お知らせ・会社情報・アクセス・製品・プライバシー資料・PDFを、トップページの要約だけで済ませず対象とする。
- 旧採用サイトの「部署紹介」と「職場の雰囲気」は `/recruit/culture/` への統合案を基準にする。
- 旧採用の複数の募集要項は**どちらが最新か人事確認が必要**。給与、勤務時間、福利厚生などを推測で一本化しないこと。
- 実績・事例ページは内容や掲載許可が確認できなければ、架空の事例を表示しない。

## 4. デザイン維持ルール（最重要）

現在のv4は、Solvvyのような高品質な企業サイトに見られる大胆な文字組み・余白・スクロール演出を研究し、**コアフューテック用に独自設計した試作**です。Solvvyのコード・画像・文言はコピーしないこと。

必ず残す設計要素：

- 日本語：`Noto Sans JP`、英字：`Poppins` を中心とするタイポグラフィ。特大英字見出しと小さな補助ラベルの階層。
- 青 `#095cff` 前後、濃紺、明るい余白のメリハリ。既存のトークンを基本とし、全ページを同じ背景色にしない。
- 浮遊感のある固定ヘッダー、**ホバー・フォーカスで開くメガメニュー**。下層ページへのリンクは実際に機能させる。
- 見出しが**左から滑り込む**演出、右から左へ流れるシームレスな英字マルキー、CTA・サービスのホバー。
- トップの**スクロール量と連動して重なり・縮小・移動するカード**。単なる一度きりのフェードインに置き換えない。
- `/services/`、第三者検証、開発、企業情報、採用、求人などの**ページごとの異なる構図・写真エリア・動き・情報密度**。全下層を同じカードテンプレートへ戻さない。
- PCとスマートフォンのレスポンシブ、キーボード操作、`prefers-reduced-motion`。

文章が増えてレイアウトが崩れる場合は、**既存の美観を維持できる範囲で行数、横幅、グリッド、セクション分割、文章量を調整**してください。既存の色・フォント・余白・インタラクションを、確認なく全面変更しないこと。視覚上の大幅変更が必要なら、変更理由と提案を先に報告してください。

写真は実際の社員・オフィス・機材・プロジェクト等の**権利確認済み実写**が望まれます。未提供の場合は写真枠と必要素材リストを作り、架空の人物を社員のように表示しないこと。

## 5. HTMLとCSS/JavaScriptを明確に対応づける（必須のリファクタリング）

現在の `style.css` と `page-variants.css`、`motion.js` に処理が集まっています。**ページごとの専用ファイルと、全ページ共通ファイルを分離**してください。

推奨構造（必要に応じて調整可）：

```text
assets/
  css/
    common.css                 # リセット、トークン、基本文字、共通UI
    components/
      header.css               # 全ページ共通のヘッダー・メガメニュー
      footer.css               # 共通フッター
      buttons.css              # 共通CTAやボタン
    pages/
      home.css                 # /index.html 専用
      services.css             # /services/index.html 専用
      third-party-verification.css
      software-development.css
      company.css
      recruit.css
      recruit-work.css
      recruit-jobs.css
      ...                      # 各HTMLに対応する専用CSS
  js/
    common/
      navigation.js            # 共通メガメニュー・モバイルナビ
      reveal.js                # 共通見出し出現の動き
    pages/
      home.js                  # カードスタック・マルキー等のトップ専用
      services.js              # 固有の動きがあるときのみ
      recruit.js
      ...                      # 実際に必要なページだけ
```

**各HTMLは共通CSS/JSと、そのページに必要な専用CSS/JSだけを読み込むこと。** 例えば `/recruit/work/index.html` にトップ専用のスタック演出JSは読み込ませないでください。共通の機能は重複コピーせず共通ファイルへ集約してください。JSが不要なページは専用JSを作る必要はありません。

CSSは各ページのルートクラス等でスコープを限定し、他ページへの意図しない影響を防ぐ。過剰な `!important`、CSSの重複、未使用スタイル、巨大な全ページ共通ファイルを避けること。

**HTMLとCSS/JSの対応を `docs/ASSET_MAP.md` に記録**してください。`build.mjs` が出力する各HTMLの `<link>` と `<script>` を正しい相対パスへ更新し、ネストした `/recruit/.../` などでもリンク切れがないことを検証してください。

## 6. 実装方法と制約

- 静的なHTML/CSS/JavaScriptで完成させる。**WordPressの導入、CMS接続、外部公開は今回行わない**。
- `dist/` は生成結果。**`dist` のHTMLだけを直接編集して終わらないこと**。編集対象は `build.mjs` とその参照元データ・CSS・JS。必要ならページコンテンツを `content/` のJSON/Markdownへ分離し、生成時に読み込む構成にする。
- 現行サイトのテキスト・画像・PDFを取得する際は、著作権や利用権限を確認する。自社公式の資料も取得可否が不明なら記録する。
- 問い合わせ・採用応募フォームは送信できないことを明示する。ダミー送信を本番機能と誤認させない。
- 既存の変更履歴を尊重し、必要なら着手前にGitコミットで退避する。ユーザーの既存ファイルを無断削除しない。

## 7. 作業順序

1. ZIPプロジェクト、全Markdown、実装コードを読み、現状と不足を短く説明。
2. 企業・採用サイトを可能な限り調査し、URLとコンテンツの台帳を作成。
3. 出典に基づいてページ構成と掲載文章を確定。意味の変わるものは保留し、必要な確認事項を整理。
4. まず現行情報をページへ反映。原文の質を高めてもよいが、専門性と事実を守る。
5. **HTML単位のCSS/JS分割**を行い、見た目と動きを維持してビルドを通す。ページ内容が増えても他ページに影響しない構成にする。
6. PC・スマホの見た目、リンク、スクロール、メニュー、操作性、アクセシビリティを可能な範囲で検証。ブラウザ検証できない場合は実施済みと書かない。
7. 最後に変更点、改善文、未取得箇所、要確認事項、検証結果を報告し、**ソース・生成済みサイト・MarkdownをZIPにまとめる**。

**検証の最低条件：** `node build.mjs` 成功、JSの構文チェック、生成された全HTMLの相対リンク・CSS/JS参照先の存在確認、PC/モバイルのレスポンシブ確認（実行可能な環境に限る）、主要ナビ・ホバー・スクロール演出の動作確認（実行可能な環境に限る）。

## 8. 完了時に必要な成果物

- 内容を反映した静的サイト一式（ソース＋`dist/`）。
- `docs/CONTENT_INVENTORY.md`：原文、出典、URL、移行先、取得状況。
- `docs/CONTENT_CHANGE_LOG.md`：意味に関わる原文⇔改善案の比較。
- `docs/ASSET_MAP.md`：各HTMLと対応CSS/JSの一覧。
- `docs/DECISIONS_AND_OPEN_QUESTIONS.md`：判断・未確認・矛盾。
- `docs/QA_REPORT.md`：確認したこと・未確認のこと・リンク切れ・表示崩れ等。
- 最終ZIP。サイト公開やWordPress化はしない。

**重要：** 現行サイトの情報へアクセスできない場合、取得していない情報を創作して埋めないでください。その範囲を明示し、取得できた部分の安全な作業だけ進めてください。特に求人条件・個人の在籍情報・法定表示に矛盾がある場合は、人による確認を待つこと。
